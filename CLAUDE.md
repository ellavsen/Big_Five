# CLAUDE.md — Neuro

Telegram-бот, который в форме живого разговора собирает психологический профиль
и выдаёт «мягкий синтез» + практические рекомендации (Akme-вектор).
Язык интерфейса, промптов и всех пользовательских текстов — русский.

Общие правила работы с кодом лежат в CLAUDE.md уровнем выше и в репозиторий
не входят. Ниже — только то, что специфично для этого проекта.

## Как я работаю (обязательно)

Цикл на каждый этап: **audit → confirm → implement → test**.

1. Сначала показать: что понял, план, список файлов, которые тронешь, и риски.
2. Пауза. Ждать «ок». Без подтверждения код не менять.
3. После «ок» — внедрять и показывать диффы.
4. Прогнать verify-критерий этапа и показать вывод команд.
5. Один этап за раз, не забегать вперёд.

Границы: менять только то, что требует задача; не рефакторить вокруг; не вводить
абстракции и не проектировать «на будущее»; перед изменением схемы БД, миграцией
или правкой конфига — сначала план, не применять молча. Если выбираешь из
нескольких путей — дать рекомендацию, а не полный обзор.

## Что сохранить любой ценой

Это и есть ценность проекта. Если рефакторинг ломает один из пунктов —
**остановиться и предупредить**, а не «упрощать до неузнаваемости».

- **Consent-first синтез («2612-правило»)**: итог выдаётся только после явного
  подтверждения пользователем (кнопка «✅ Подвести итог»).
- Тёплый, неоценочный тон промптов: «не диагноз, а вероятности».
- Накопление доказательств вместо преждевременного типирования.
- Разделение «ядро vs роль/компенсация».
- Детерминированные модули отдельно от LLM — интерпретируемо и дёшево.
- `energy_economy`, `compensation_patterns`, `team_mirror`, `role_vs_core` — это ядро
  будущего продукта «управление энергией», а не второстепенная логика. Усиливаем, не режем.

## Целевое видение

Neuro = инструмент управления собственной энергией и командной динамикой,
а не «ещё один MBTI-тест».

- **B2C-ядро**: личная карта энергии — опоры / восстановление / среда / риски выгорания;
  профиль растёт во времени.
- **Задел под B2B**: обезличенная агрегированная карта энергии команды — это `team_mirror`,
  доведённый до продукта.
- **Методология**: Big Five (OCEAN) — научное ядро; MBTI-4-буквы — популярная обёртка,
  в UI и промптах явно помечена как интерпретация, а не истина. Маппинг приблизительный
  (E/I↔Extraversion, S/N↔Openness, T/F↔Agreeableness, J/P↔Conscientiousness) — так и подписывать.
- **Поведенческие индикаторы** (энергия / компенсации / роль) — главный дифференциатор,
  живут отдельным слоем.

## Как запускать

Python 3.12 (3.13 несовместим с `python-telegram-bot==20.7`). Всё из корня проекта.

```bash
source venv/bin/activate
python -m app.main          # Telegram-бот
pytest -q                   # тесты
ruff check app core modules tests
```

`.env` (в git не попадает, шаблон — `.env.example`):
`OPENAI_API_KEY`, `OPENAI_MODEL`, `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`.

База: PostgreSQL 16 через Homebrew, база `neuro_db`, схема разворачивается
`init_db()` при старте бота (`create_all`, не Alembic — новые колонки в уже
существующую базу сами не доедут).

## Архитектура (как есть, без мнимой мультиагентности)

```
app/telegram_bot.py (Telegram I/O, USER_STATES in-memory)
  → core/orchestrator.py  один планировщик хода: модули → валидность → черты → LLM
      → core/llm.py       OpenAI (plan_turn / synthesize)
      → modules/          детерминированные детекторы + registry.MODULES
      → core/validity.py  валидность, закрытие черт, критерий 2612
      → core/scoring.py    MBTI как производная от черт (только для показа)
      → core/transitions.py  выбор режима хода и приоритетной цели
      → core/db/          SQLAlchemy async → Postgres (repo.py — единственный слой доступа)
prompts/  turn_planner.md и synthesizer.md — оба загружаются, мёртвых промптов нет
```

**Агентов нет.** `chosen_agent` — это режим одного планировщика хода
(`diagnost` — вопрос, `interpreter` — короткое отражение, `synthesizer` — итог),
а не отдельная модель и не отдельный промпт. Режимы диалога живут внутри
`turn_planner.md`, синтез — отдельным вызовом. Поле называется «агентом» по
историческим причинам; переименование потащило бы за собой сохранённое
состояние в `sessions.state_json` ради косметики.

`modules/synthesizer.py` — детерминированный разбор черт (`core / compensated / boundary`),
подключён в промпт синтеза полем `deterministic_profile`. Признак компенсации читается
из `state.notes` (модули пишут туда `compensation:control`).

## Память между разговорами

При создании новой сессии в состояние кладётся `previous_profile` — дата прошлого
итога, черты и до 5 заметок. Оттуда уходит в оба промпта.

- **Прошлый текст итога в память не кладём**, только черты и заметки: целиком он
  длинный и уводит модель в пересказ вместо наблюдения.
- У модели в памяти нет самого разговора — только числа. Промпты явно запрещают
  выдумывать эпизоды «в прошлый раз вы говорили, что…».
- Задача синтеза при наличии памяти — показать, **что изменилось**, а не собрать
  профиль заново. Рост `neuroticism` между разговорами — самое ценное наблюдение.
- Битый профиль от старой версии контракта → просто нет памяти, диалог не ломается.

## Ядро оценки — Big Five, не MBTI

Сбор идёт по пяти чертам (`Trait`), направление — `high` / `low`.

**Neuroticism — не пятое колесо, а главная черта продукта.** У неё нет пары в MBTI,
и пока черт было четыре, наблюдения про энергию класть было некуда: `energy_economy`
на «расслабилась» выдавал сигнал Sensing. Из неё же строится блок про выгорание
в `/akme`. Не занижать её «из вежливости» — это про цену нагрузки, а не оценка.

**MBTI — производная.** Считается в [core/scoring.py](core/scoring.py) из четырёх
черт (Neuroticism не участвует), показывается только целиком и только с оговоркой.
Никогда не собирать сигналы «в MBTI» и не показывать `probabilities` из ответа
модели: это второй источник типа, и он спорит с ядром.

## Тему хода выбирает код, а не модель

Планировщик, оставленный решать «о чём спросить дальше», отзеркаливает тему
собеседника. Живой диалог: человек говорил про усталость и получил **семь вопросов
подряд про восстановление**, пять наблюдений по одной черте и ноль по остальным.
Подсказка `trait_observations` внутри JSON-контекста этого не переломила — правило
из середины промпта стабильно проигрывало остальным блокам.

- Банк житейских ситуаций — [core/probes.py](core/probes.py), выбор —
  [core/coverage.py](core/coverage.py). Ситуация уходит в промпт **приказом перед
  данными**, а не ключом внутри объекта состояния. Это единственное размещение,
  которое сработало.
- Ритм: ситуация → **одно** углубление по детали рассказа → новая ситуация.
  Без потолка получаются те самые семь вопросов; без углубления — анкета.
- Использованные ситуации помечаются в `state.used_probes`, повтор невозможен
  физически, а не «не рекомендуется промптом».
- **Никаких вариантов ответа в вопросе.** «Большая компания или три человека?» —
  это тест с вариантами: человек выбирает ярлык вместо рассказа, а два полюса
  прямо называют измеряемое. Держится тестом `test_probes_offer_no_answer_options`.
- Формулировки — без рода. Русское прошедшее время его выдаёт, а пола собеседника
  система не знает: первый же вопрос звучал «как ты провёл выходные» для женщины.

**Порядок полей в `TurnPlan` значим.** Модель заполняет их сверху вниз, и пока
`message` стоял первым, она сочиняла вопрос, а наблюдения дописывала по остатку:
рассказ про ссору и примирение давал **ноль** наблюдений. Сейчас первым идёт
`scan` — обязательный проход по всем пяти чертам с правом поставить прочерк
(иначе модель выдумывает под квоту). Замер на одном и том же тексте:
`0 → 1 (перестановка полей) → 3 наблюдения по 3 чертам (scan)`.

## Шкала черт: числа считает код

`trait_scores` считаются в [core/scoring.py](core/scoring.py) из накопленных
наблюдений и **перезаписывают** то, что вернула модель. Промпт получает те же
числа готовыми, но полагаться на дисциплину модели тут нельзя.

Почему забрали: на живом диалоге модель проставила все пять черт в 0.70–0.85 —
включая две, где было ровно **одно** наблюдение. Профиль, где выражено всё сразу,
ничего не различает и при этом приятно читается, потому что состоит из одних
сильных сторон. Это ровно тот эффект, от которого предостерегает README.

- **`0.5` — не «средне», а «данных не хватило».** Меньше `TRAIT_MIN_SIGNALS`
  наблюдений — черта остаётся ровно посередине, без исключений.
- Считается по перевесу ведущего направления над противоположным: два спорящих
  наблюдения оставляют черту у середины, а не складываются в уверенность.
- Дальше 0.1–0.9 не уходим никогда: это вероятности, а не диагноз.
- Проверка на реальных данных того диалога: `ENFJ → EXXJ`, выражено черт 5 → 3.

## Закрытие черт

Черта закрывается **накоплением**, а не одним ярким сигналом. Считает `weigh_trait`
в [core/validity.py](core/validity.py): вес ведущего направления, число наблюдений,
набор источников, перевес над противоположным. Пороги — в `core/config.py`.

- Инвариант: **жёстко закрытая черта всегда закрыта и мягко.** До 2C было наоборот,
  и «мягкое» условие оказывалось строже «жёсткого». Закреплено тестом.
- Модули — слабый слой (`confidence` 0.25–0.3) и в одиночку черту не закрывают:
  их тексты постоянны, а `add_signals` режет дубли по `(trait, direction, text)`.
  Закрытие требует наблюдений от LLM, у которых текст каждый раз новый.
- `direct_example=True` ставится **только** при маркере конкретного эпизода
  (`has_episode`). «Я контролирую» — самоописание, «вчера я контролировала» — случай.
- Матчинг маркеров — всегда через `find_marker`, никогда `if слово in text.lower()`:
  иначе вернётся баг «не контролирую» = контроль.
- Вес округляется: `0.6 + 0.3` в float даёт `0.8999999999999999` и не проходит порог.

## Миграции БД

`init_db()` разворачивает схему с нуля (`create_all`), но **в существующую таблицу
новую колонку не добавит**. Alembic пока не заводим, поэтому: каждая правка схемы —
нумерованный идемпотентный файл в `migrations/`, применяется вручную.

```bash
psql "$DATABASE_URL" -f migrations/001_add_sessions_state_json.sql
```

Правя модель в `core/db/models.py`, всегда пишите парный `.sql` — иначе на машине,
где база уже создана, схема разъедется с кодом.

**Миграции — только для обновления существующей базы.** На чистой всё разворачивает
`create_all`, и прогонять их там нельзя: `002` переименовывает колонку, которой
в новой схеме нет, и падает. Проверено на пустой базе.

**Грабли `JSONB`:** по умолчанию SQLAlchemy пишет питоновский `None` в JSON/JSONB как
литерал `null`, а не SQL `NULL` — строка перестаёт находиться по `IS NULL`. Для новых
JSON-колонок объявляйте `JSONB(none_as_null=True)`. У `sessions.state_json` это уже так;
у `synthesis.axes_confidence`, `synthesis.raw_json`, `akme.vector_json` — ещё нет.

## Состояние диалога

`USER_STATES` — горячий кэш, а не хранилище. Долговременное состояние живёт в
`sessions.state_json`, и любое обращение идёт через `await _get_state(user_id)`:
он выгружает протухшее, поднимает из БД недостающее и отмечает время.

- Не читайте и не пишите `USER_STATES` напрямую. Свежее состояние — `_put_fresh_state`.
- Эвиктор не трогает состояния без `session_id` — их некому вернуть из БД.
- `state_json` = сырой профиль, спецкатегория ПДн. `finish_session` его затирает;
  не сохраняйте снимок туда, где он переживёт сессию.

## Контракт LLM-слоя (не сломать)

- Обе модели (`TurnPlan`, `SynthesisResult`) уходят в API как **strict-схемы**.
  Strict не принимает открытые словари (`Dict[str, X]` → `additionalProperties`),
  `ge/le`, `pattern`, `format`. Локальный хелпер SDK это пропускает молча — отказ
  приходит от API при запросе. Guard: `tests/test_llm.py::test_schema_is_strict_compatible`.
- **Полярность осей — одна для всех: `1.0` = первая буква названия оси** (E / S / T / J).
  Задана в `modules/akme_vector.py::_dominant_letter` и продублирована в
  `prompts/synthesizer.md`. Менять только в двух местах сразу.
- `axis_map` описывает наблюдаемое поведение **целиком**, включая ролевое;
  разделение «ядро против роли» живёт отдельным полем `core_vs_role`.
- `state.synthesis` = `SynthesisResult.model_dump()`, и `/akme` читает его напрямую,
  без переходников. Переименование полей ломает `akme_vector_from_synthesis`.

## Mini App: чем доказывается, что профиль ваш

Веб-слой — отдельный процесс (`uvicorn app.web:app`), общая с ботом только база.

- **Кто спрашивает — решает только подпись Telegram.** `verify_init_data`
  в [app/webapp_auth.py](app/webapp_auth.py). Никаких `user_id` в параметрах
  запроса: подставить чужой — значит прочитать чужой профиль.
- Подпись проверяется **до** всего остального, включая `auth_date`: до неё ни
  одному полю внутри верить нельзя.
- Сравнение хешей — только `hmac.compare_digest`. Обычное `==` выходит из цикла
  на первом несовпавшем байте, и подпись подбирается по времени ответа.
  **Тестом это не ловится** — проверено ломом, все тесты остались зелёными.
- `initData` передаётся заголовком `X-Telegram-Init-Data`, не в адресе: адреса
  оседают в логах, истории браузера и `Referer`.
- Наружу уходит только производное от синтеза. `notes`, сообщения разговора
  и `probabilities` не отдаются никогда, даже владельцу.
- Причина отказа — в лог, пользователю всегда одна общая формулировка.

## Данные пользователя

Профиль — **спецкатегория ПДн**. Правила простые и нарушать их нельзя.

- **До согласия не собирается ничего.** Гейт — `_has_consent` в начале
  `handle_message` и `handle_audio`. Единственное, что известно до согласия, —
  `telegram_id`: иначе согласие не к чему привязать.
- Текст согласия и его версия — [app/consent.py](app/consent.py). **Меняете текст —
  поднимаете `CONSENT_VERSION`** в `core/config.py`, иначе люди останутся согласными
  с редакцией, которой больше нет.
- Текст **не проходил юридическую экспертизу**. Перед публичным запуском показать юристу.
- `/delete_me` работает **даже без согласия** — иначе отозвавший согласие не смог бы
  попросить стереть уже собранное.
- Ретеншен: `RETENTION_DAYS` = 180, чистка при старте процесса. Это половина решения —
  пока бот не перезапускают, просроченное лежит. В проде нужен cron или воркер.

## Известные вопросы, отложенные осознанно

- `users.telegram_id` получил ненужный `DEFAULT nextval(...)`: SQLAlchemy сделал
  BigInteger-PK автоинкрементным, хотя id приходит от Telegram.
- `stability` модель ставит «пограничная» по всем чертам сразу; `confidence` почти
  не разъезжается. Тянется с 2A, трижды подступались.
- `probabilities` в `SynthesisResult` дублирует производный MBTI и спорит с ним.
  Пользователю не показывается; поле стоит пересмотреть.
- Грабли `none_as_null` под `synthesis.raw_json`, `synthesis.traits_confidence`,
  `akme.vector_json` — те же, что чинили для `state_json` в 2B.
- `reset_cmd` и `export_cmd` не покрыты тестами и ни разу не прогонялись.
- Текст согласия не проходил юридическую экспертизу — до живых пользователей
  показать юристу.

**Правило, выведенное из сквозного прогона:** миграция, которая переименовывает
колонку, обязана проверить и её **тип**. Сверка «имена колонок совпадают
с моделью» пропустила несовпадение `varchar(8)` против `String(24)`, и наблюдения
молча не сохранялись. Проверять типы, а не только имена.
